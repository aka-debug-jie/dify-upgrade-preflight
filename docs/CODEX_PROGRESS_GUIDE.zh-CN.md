# 后续推进全步骤与 Codex 引导指南

本文件是操作指南，不是新的任务状态源，也不构成任何审批。契约和原阶段提示词保持原样，实时状态只读 roadmap.yaml。编写时 P00=ready_for_review、P01=blocked_review、真实规则与支持边批准数为零。

## 先理解你的工作量

你不必逐行指导代码。每阶段主要做三件事：确认本轮目标；看真实演示、失败案例和验证记录；决定是否通过验收。实现、局部修复、测试、证据整理交给 Codex 在授权范围内完成。

推荐循环：阶段授权 → 本阶段实现与测试 → ready_for_review → 单独审查 → 修复与复查 → 你明确验收 → 记录批准对象/摘要 → done → 明确授权下一阶段。阶段可以跨多个会话；不要因为会话结束强行完成阶段。

OpenAI 官方提示建议强调目标行为、相关文件/复现步骤、约束和验证方式。本指南按这些要素组织；阶段审批与禁止事项来自本项目契约，而非官方通用要求。[官方 Prompting 文档](https://learn.chatgpt.com/docs/prompting)

## 第三步：每阶段统一审查、修复、审批

### 审查：建议开一个单独会话

实现会话与审查会话分开，能减少直接沿用实现者结论的机会，但另一个 Codex 审查仍不能替代人工规则裁决或独立部署反馈。无需把整个项目推翻重读，提供当前阶段和交接路径即可。

```text
本轮只审查，不实现新功能，不验收阶段。
读取 prompts/REVIEW.md，审查当前 ready_for_review 阶段。
先读本阶段契约、固定 fixture 与证据，再看实现和执行记录。
交接入口：<实际 HANDOFF 路径>。
核验与阶段风险相称的命令，不能只照抄测试总结。
给出 PASS_FOR_OWNER_REVIEW、CHANGES_REQUIRED 或 BLOCKED_EXTERNAL。
每个问题给文件位置、复现证据、影响和最小修复建议。
本轮只新增审查报告，不修改业务代码、契约、原验证记录或审批状态。
```

### 修复：回到实现会话

```text
请处理 <实际审查报告路径> 的已证实问题，仅限当前阶段。
先复现问题，再最小修复，增加对应反例并运行相关回归。
```

## 四个额外审批节点如何处理

**真实规则（P05）：** 先要求完整 RULE_REVIEW 卡、固定来源、精确边、必要 facts、正/反/unknown/边界案例、测试结果与候选 digest。你批准的是明确的规则 ID、内容摘要和精确边，不是“这批规则以后都可以”。如需进一步修规则，重新核对批准是否有效。

```text
我批准以下已经审阅的候选规则及支持边晋升：
<逐条规则ID、内容摘要、支持边ID/摘要、审核卡路径>。
批准仅限上述内容；请核验摘要与测试结果后记录审批并晋升。
其他候选保持未批准；如内容不同，先展示差异，不沿用这次批准。
```

**实验（P08）：** LAB_PLAN 必须列出独立资源身份、镜像、合成数据、允许挂载、具体命令、副作用、成功条件及精确回收方案。先看计划，再授权明确资源和动作。产品仍不具有升级能力；实验脚本的权限不能流入产品。

```text
我批准执行 <LAB_PLAN路径与摘要> 中列明的实验动作，
仅限 <独立VM/专用daemon标识> 和计划所列合成数据、镜像及资源。
请先核对环境身份与批准对象；不使用生产context或生产卷。
超出该资源与动作清单的内容不在本次批准内。
执行后保存原始结果和脱敏交接，不扩大成功结论。
```

**发布（P09）：** 先运行发布材料准备流程。你之后只授权具体渠道、仓库、版本、构建摘要和动作。当前没有 Git 仓库；如需要 Git init 或远程仓库，单独授权，远程仓库默认私有。不要在批准模板中写入 token。

```text
我批准对 <明确仓库/渠道> 执行 <逐项列出的动作>，
仅发布 <包文件/版本/sha256>，依据 <发布计划路径及摘要>。
没有列出的 commit、push、tag、上传、仓库创建或外部沟通均不在授权内。
先核验对象一致，再执行；内容发生变化先展示差异。
```

**范围或验收变更：** Codex 应先依据 templates/CHANGE_REQUEST.md 提交原因、证据、收益/代价、受影响文件和新旧标准差异；你明确批准后才允许修改。允许提交提案不等于允许立刻降低阈值。缺乏六类根因时允许说 NO-GO，不允许悄悄把六改成二。

## 遇到中断、卡住或跑偏时怎么说

**换会话或隔天继续：**

```text
请按 prompts/RESUME.md 接手，从 roadmap.yaml 和最新有效交接恢复。
不要重新规划或重建项目，不依赖聊天中的“已完成”判断状态。
先核查真实依赖与审批，仅继续当前已授权但尚未完成的任务。
若处于 ready_for_review，仅展示待审证据，不擅自开始下一阶段。
```

**卡住了：**

```text
请给出当前阻塞的最小复现、实际命令/返回码、已尝试的方法、
属于实现问题/缺环境/缺证据/待审批的哪一类，以及可继续的独立工作。
已授权的普通修复请继续；需要我决定的只提出具体可审对象。
不循环重试同一失败，不更换标准，不把未测写成通过。
```

**开始铺框架或扩功能：**

```text
请回到当前阶段的验收目标，指出新增内容对应哪一条已授权任务。
没有对应任务的工作先停止，把建议记为后续提案。
优先完成一条真实可运行的本阶段闭环，并给出最小验证。
保留已有文件，不为纠偏删除用户改动或重建整个仓库。
```

**出现疑似错误放行或泄密：** 使用 prompts/INCIDENT_FALSE_SAFE.md；停止受影响结论和发布，保留脱敏复现证据，修复后补反例并复审。不要粘贴真实凭据到会话里。

## 每次收到“已完成”，你固定问这六件事

1. 本阶段新增了什么可直接观察的行为？给一个可复现输入和输出。
2. 正例之外，反例和关键未知分别得到什么结果？
3. 哪些命令真的跑过，原始记录在哪，哪些没跑？
4. 有没有修改契约、expected、规则范围或阈值？有则对应批准是什么？
5. 还有哪些条件依赖推测、外部环境或人工证据？
6. 当前应为 ready_for_review、blocked_external 还是 blocked_review？唯一下一步是什么？

审查深度按风险分配：P01/P03/P06 重点看闭环、语义和安装；P02/P04/P05/P07/P08 重点看秘密、未知、权限和证据。P09 的外部动作必须明确审批。无需每次重复无关全套性能测试，但不能漏掉阶段要求的验收。

## 如何安排模型与并行工作

沿用你现有的角色契约：复杂实现由主代理完成；安全、规则与最终复核用强审查角色；明确局部代码任务才交 Spark；机械只读核查交 Luna；大范围只读取证交 Terra。只有运行时确实提供对应模型、effort 和日志证明时才认定路由成功，不因 task_name 相同就认为已加载角色。

本项目起步建议一个实现主会话、一个单独审查会话；只在存在明确独立任务时增加只读取证工作。你的 32 实例是上限，没必要在小阶段用满。分工必须指定文件所有权，不让多个执行者同时改 verdict、schema 或 roadmap；角色边界、失败最多一次重试、停止升级条件仍按现有用户指令执行。

## 怎样少操心又不失控

每次任务只补充本轮变化：阶段、已有批准、当前问题、输入/交接位置和停止点。长期要求保留在项目文档；不要每轮粘贴 ALL_PHASE_PROMPTS.md。普通实现选择交给 Codex；你集中审核规则、范围、阶段、实验和发布。

让 Codex 自主完成当前已授权阶段的修复闭环；需要你审批时，应先准备具体文件、摘要、测试与风险。避免仅凭“看起来可以”批准；也不需要为变量名和文件拆分反复决策。

本指南没有调整 roadmap、审批记录、阶段提示词或受保护文件。后续状态始终以实际文件与审批为准。
