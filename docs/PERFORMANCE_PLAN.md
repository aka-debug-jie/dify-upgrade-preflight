# 性能与工程效率执行方案

所有阈值来自 ACCEPTANCE_CONTRACT；本文件定义如何测，不宣称已经达标。

## 1. 先优化哪件事

最先消除重复工作：一个采集请求最多一次原生归一化每个明确配置组合；catalog 一次加载和验证；同一基线一次索引；规则只访问类型化 facts。

不引入缓存数据库、多进程常驻服务、LLM 或 GPU。先 profile，只有确认热点后才增加缓存或并发。

## 2. 工作负载

`help`：安装完成后的新 Python 进程，不含 pip/uv 首次下载。
`medium`：固定种子 60 服务、2,000 facts、250 rules、输入 ≤ 2 MiB。
`stress`：200 服务、10,000 facts、1,000 rules、输入 ≤ 12 MiB。
`compose`：显式文件清单 ≤ 100、总输入 ≤ 32 MiB，使用冻结 Compose 版本。

构造器必须生成真假/未知混合规则、实际访问的事实和实际可比较的字段。不能生成 1,000 条全部不适用规则来美化速度；记录匹配率和 unknown 数。

## 3. 测量方法

每组 5 次预热、30 次正式独立进程，使用 monotonic/perf_counter。保存原始样本、p50/p95/max、峰值 RSS、退出码、机器资源和 git/worktree 标识。

Linux ru_maxrss 的单位与其它平台可能不同；适配或统一外部采样，不直接比较原始数字。新进程启动开销计入 check；原生 Compose 子进程的内存/耗时单独记录。

离线核心不访问网络，必须通过 socket monkeypatch/系统隔离证明，而不是仅观察“看起来没联网”。原始业务配置不能进入 benchmark 产物。

## 4. 硬资源上限

产品输入：snapshot ≤ 16 MiB；配置单文件 ≤ 2 MiB、≤ 100 文件、总 ≤ 32 MiB；本地规则目录 ≤ 5 MiB、≤ 1,000 条；表达式深度 8、节点 64；子进程输出 ≤ 32 MiB。

超限：明确的 ERROR/采集失败，不跳过多余输入后继续给通过。

超时：单个 Compose 子进程 15 秒，总采集 30 秒；回收进程组，stderr 同样限制。不能无限 retry。

## 5. 性能退化

同一参考环境相对基线 p95 恶化超过 20% 或越过硬阈值，记录 profile 并阻止完成性能阶段。波动用重复测量确认；不立即放宽 SLA。

共享 CI 只比较趋势，正式绝对门禁放在声明的参考机。没有参考机时状态为“未测”，不是“通过”。

## 6. 开发效率

日常先跑受影响 unit/contract，再跑完整快套件；跨模块接口变更触发全套。Docker 重演不每个小提交都跑，但支持边/采集语义改动必须跑。

每阶段先完成一个可验收任务再做下一个，不要求一天完成某个数量。禁止以加线程或生成更多代码代替产品问题验证。
