# 发布、真实用户验证与长期维护

## 1. 三种不同完成状态

工程候选完成：P00–P07 的本地证据齐全。
实验 beta 完成：P08 重演与画像验证通过，仍不是生产担保。
公开/稳定交付：P09 获发布授权，并收集规定的真实使用反馈。

状态名称不替代实际证据。没有发布权限可以停在 ready_for_review，不能私自上传 PyPI 或推送。

## 2. 发布清单

固定代码和 catalog 内容；复查审批哈希；安装 wheel/sdist；所有输出脱敏；LICENSE/归属核验完成；README 明确 support edges、scope、未知和非目标；SECURITY/贡献规则/故障报告说明齐全。

当前启动包不替你选择最终许可证或声明拥有 Dify 商标。P00 核验来源再分发条件，P09 由你批准项目许可证。不要把上游完整源码打进工具包。

包里只含本工具代码、schema、批准规则、少量公开必要数据和 synthetic demo；不含原始 `.env`、真实 hosts、日志、数据库、未批准规则、模型输出草稿。

## 3. 发布授权必须具体

授权应列明：仓库、commit/tag、构建 artifact digest、catalog version/digest、发布渠道、是否允许 push/tag/upload。没有明示的行为不做。

生成 release note 或本地构建不等于授权发布。凭据只能通过用户配置的安全机制使用，不进入聊天和配置文件。

## 4. 用户验证

目标是 ≥3 个不同画像，且 ≥2 个独立维护者实际使用；记录安装成功与否、发现的有效问题、误报、不可判断项、再次升级是否复用。不默认遥测，不收真实配置。

首次发布后的评估可按 30 天观察窗口组织，但不是自动后台承诺。Star 仅作辅助观察；保留/停止依据是工具是否节省复核工作、能否让人采取明确行动。

可继续：有复用、有实际故障被发现、误报可控、维护一条新版本边成本可接受。
应调整：普遍不愿安装、只看 env 差异、关键状态总不可知、你无法追踪版本维护。

## 5. 更新规则

新 release → 固定来源与源码 → 差异候选 → 检查是否替代旧手工步骤 → 三态和边界 fixtures → 独立审查 → owner approval → 新 catalog 构建 → 回归旧路径。

检测上游变化可以写成手动脚本；任何 GitHub 定时任务和自动发 PR 均需额外授权。自动任务只能生成候选，不直接批准或发包。

## 6. False-safe 事件

先停止推广受影响边，发布状态由用户批准；保留脱敏证据；必要时把该边撤为 INCOMPLETE/UNSUPPORTED；加入最小失败 fixture；根因分析；修复和反例；重新审核；通知已知用户。

不要悄悄只改 README 或删测试。事件报告要说明影响边界，不夸大或缩小已知影响。
